RESOLVED 2026-09-19 (kept here for the record, not action items)
---------------------------------------------------------------------

- OpenAILLMService.Settings in app/main.py's _build_llm now passes
  extra={"reasoning_effort": "none"} — required for gpt-5.6-luna to
  accept function tools on /v1/chat/completions at all (400s otherwise).
  Confirmed harmless against gpt-5.4-nano too, so safe if OPENAI_MODEL
  is ever reverted.

- app/pipeline/logging_enforcer.py's _backfill_log_interaction call
  (separate AsyncOpenAI client, also attaches tools) hit the identical
  400 in a live /live test — found from a real traceback, not caught
  ahead of time. Fixed with the same reasoning_effort="none".

- app/pipeline/transcript.py's generate_call_summary used the legacy
  max_tokens=120 param, which gpt-5.6-luna rejects outright ("Unsupported
  parameter: 'max_tokens' ... Use 'max_completion_tokens' instead") —
  also found from a live traceback. Fixed to max_completion_tokens=120,
  confirmed working against both gpt-5.6-luna and gpt-5.4-nano.

- /live's "Data channel not established within 10s after connection"
  warning (and the "disabling future queueing" that follows). Root
  cause: app/live_client.py's hand-written JS never called
  pc.createDataChannel(...); pipecat's SmallWebRTCTransport passively
  waits for the client to open one and times out after 10s if it
  doesn't. Confirmed via two independent from-scratch test server runs
  that this was 100% reproducible, not a one-off — and confirmed via
  real end-to-end test calls (fake mic audio, real Sarvam/OpenAI) that
  it never actually broke the conversation; audio flows over a separate
  track. Fixed with one line (pc.createDataChannel('events')), re-tested
  clean. Structurally cannot affect real telephony calls — those use
  FastAPIWebsocketTransport, no ICE/data-channel concept at all. Full
  writeup in TROUBLESHOOTING.md.

- Fallback TTS voice gender mismatch: OPENAI_TTS_VOICE was "shimmer"
  (female) while the primary Rumik voice is "adam" (male) — a caller
  could hear the bot's voice flip gender mid-call on a Rumik failure.
  Fixed: OPENAI_TTS_VOICE changed to "echo" (male-sounding) in .env,
  .env.example, and the code default.

- TROUBLESHOOTING.md didn't exist despite being referenced by
  call_health.py and resilient_stt.py. Now exists, and is thorough —
  covers CALL_HEALTH log shapes, both real prod-crash incidents from
  today (with commit hashes), API key rotation checks, and more.

- The root cause behind today's two production outages (code
